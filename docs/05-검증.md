# 05. 검증

작업협약 3번: **"다 된 것 같다"로 끝내지 않는다.**
아래는 각 단계에서 실제로 돌려서 pass/fail 이 나오는 수단이다.

## 1. 상태 판별이 실제와 맞는가 — 가장 중요

이 도구의 가치 전부가 여기 걸려 있다.

```bash
java -jar build/libs/claude-board.jar --json | jq -r '.projects[] |
  "\(.current.state)\t\(.name)\t\(.current.title // "-")"'
```

**눈으로 대조한다.** 각 세션의 Cursor 창을 열어 실제로 답변 대기 상태인지 확인.

합격 기준: 살아있는 세션 전부에 대해 판별이 일치.
불일치가 하나라도 있으면 `collect/StateResolver.java` 를 고친다.

### 반드시 넣을 단위 테스트

```
① 마지막이 assistant                     → waiting
② 마지막이 user + tool_result 블록 포함  → working   ← 이걸 빠뜨리면 상태가 뒤집힌다
③ 마지막이 user + 순수 텍스트            → working
④ 파일이 비어 있음                       → 예외 없이 부분 결과 반환
⑤ 마지막 줄이 깨진 JSON                  → 그 줄만 건너뛰고 계속
```

②가 핵심이다. 도구 결과가 `type: "user"` 로 기록되므로
순진하게 짜면 "작업 중"과 "답변 대기"가 정확히 반대로 나온다.

### 되돌리기 검증

②의 판별 로직을 일부러 제거하고 테스트가 **빨개지는지** 확인한다.
통과만 보고 넘어가지 않는다.

## 2. 성능

```bash
time java -jar build/libs/claude-board.jar --json > /dev/null
```

목표: **200ms 이내.**

### ⚠️ 비교 대상은 `cat` 이 아니라 실제 파싱이다

`cat` 은 바이트로만 읽어 OS 페이지 캐시 덕에 비현실적으로 빠르게 나온다
(실측 171ms — 역순 리더와 차이가 없어 보인다). **JSON 파싱까지 해야 공정하다.**

```bash
./gradlew test --tests '*ReaderBenchmark*' -Dbenchmark=true -i
```

실측 (2026-09-03, 파일 109개 / 총 327MB / 최대 21MB):
```
역순 리더:         86ms
전체 파싱(148727줄):  1369ms
배수:           15.9배          ← "10배 이상" 기준 통과
```

### 전체 갱신이 200ms 를 넘으면 어디가 병목인지 나눠 재라

`--json` 전체는 285ms 로 목표를 넘는다. 구간을 나눠 보면:

```bash
# claude agents --json 단독 5회
201ms 202ms 207ms 204ms 199ms
```

**~200ms 가 `claude agents --json` 서브프로세스**(Node CLI 부팅)로 저장소 밖이다.
리더를 더 조여도 소용없고, `@Scheduled` 캐시로 푼다.
→ "느리다"를 봤으면 **어느 구간인지 먼저 재라.** 엉뚱한 곳을 최적화하게 된다.

## 3. 데이터 정확성

```bash
# 살아있는 세션 수가 일치하는가
diff <(claude agents --json | jq 'length') \
     <(java -jar build/libs/claude-board.jar --json | jq '[.projects[].current, .projects[].others[]] | length')

# 컨텍스트 토큰이 그럴듯한가 (0 이거나 비정상적으로 크지 않은지)
java -jar build/libs/claude-board.jar --json | jq -r '.projects[].current | "\(.name)\t\(.contextTokens)"'

# 파싱 실패가 조용히 묻히지 않는가
java -jar build/libs/claude-board.jar --json | jq '.errors'
```

## 4. 보안 경계

**서버가 떠야 가능하다.** #5 에서 처음으로 실제 수행했다.

```bash
# 127.0.0.1 외에 열린 포트가 없어야 한다
lsof -nP -iTCP:7777 -sTCP:LISTEN
# → 127.0.0.1:PORT 만 나와야 함. *:PORT 나 0.0.0.0 이 보이면 실패

# 외부에서 접근이 막히는지 (tailnet 주소로 시도)
curl -m 3 http://$(tailscale ip -4):7777/api/sessions   # → 연결 거부되어야 정상
```

실측 (2026-09-03, #5):

**자원(포트)으로 센다.**

### SSE emitter 정리

누수는 예외를 내지 않고 조용히 쌓인다. 붙였다 끊고 **실제로 걷히는지** 본다.

```bash
# 연결 5개를 붙여둔 상태에서
jcmd <pid> GC.class_histogram | grep -iE "SseEmitter|StreamController"
# 모두 끊고 하트비트 주기(기본 15초)를 기다린 뒤 다시
```

⚠️ **"0" 만 보고 통과시키지 말 것.** 0 이 "정리됐다"인지 "측정이 안 된다"인지
구별되지 않는다. **연결 중일 때 실제로 세어지는지를 먼저 보인 뒤** 0 을 근거로 쓴다.

실측 (#5): 연결 5개일 때 `SseEmitter` 5개가 세어졌고, 끊은 뒤 0 이 됐다.
`lsof -nP -iTCP:7777 | grep -c ESTABLISHED` 도 0.

## 5. 프론트

- 세션이 **0개**일 때 화면이 깨지지 않는가
- 제목이 없는 세션(`aiTitle` 부재)이 있어도 렌더되는가 — 실제로 존재함
- 아주 긴 브랜치명(`worktree-fix-retry-throttle`)이 레이아웃을 깨지 않는가
- SSE 연결이 끊겼다 붙을 때 중복 렌더가 없는가
  (서버는 과거 이벤트를 재생하지 않고 이벤트 id 도 쓰지 않는다 —
   클라이언트가 `Last-Event-ID` 로 재생을 요구하지 않게 하려는 것이다.
   [02-백엔드](02-백엔드.md) "중복 렌더 방지")
