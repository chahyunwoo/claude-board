# 00. 개요

## 문제

Claude Code 세션을 여러 프로젝트에 걸쳐 동시에 띄워두고 작업한다.
컨텍스트 관리를 위해 **프로젝트마다 일정 범위가 되면 새 세션을 여는** 방식이라
세션이 계속 쌓인다.

그 결과 지금 알 수 없는 것들:

- 어떤 세션이 **내 답을 기다리는 중**인가
- 어떤 세션이 **멈춰 있는가** (죽었거나 막혔거나)
- 각 세션이 **무슨 작업**을 하던 중인가
- **컨텍스트가 얼마나 찼는가** — 새 세션을 열 시점인가

### 실측 (2026-09-03, 맥북프로)

```
$ claude agents --json | jq length
10                       # 살아있는 세션

$ ls ~/.claude/projects | wc -l
21                       # 프로젝트

세션 기록 총 109개, 최대 파일 5.8MB
10개 중 7개가 사용자 답변 대기 상태였음
'for-projects' 세션은 27일째 떠 있음
```

`claude agents --json` 이 살아있는 세션 목록을 주지만 **무슨 작업인지·어느 브랜치인지·
답을 기다리는지는 알려주지 않는다.** 그 정보는 세션 기록 파일에 따로 있다.
이 둘을 잇는 것이 이 도구의 존재 이유다.

## 목표

1. **프로젝트 단위**로 현재 상태를 한 화면에
2. **답변 대기** 세션을 최상단에 — 가장 높은 가치
3. **컨텍스트 사용량**과 경고 — 새 세션 시점 판단
4. 조회 전용. 세션을 조작하지 않는다

## 원칙

### 데이터는 기계를 떠나지 않는다

각자 자기 데이터만 본다. 중앙 서버·계정·외부 전송 없음.
백엔드는 `127.0.0.1` 에만 바인딩한다.

이유: 세션 기록에는 프롬프트 전문·절대 경로·브랜치명·PR 정보가 들어 있다.
남의 기계 데이터를 보관하면 유출 시 우리 책임이 된다.
개인 도구에서 그 책임을 질 이유가 없다.

### 조회 전용

세션 종료·재개 같은 조작을 넣지 않는다. 잘못 눌러 작업이 날아가는 위험 대비
얻는 편의가 작다.

### 읽기는 파일 끝에서부터

세션 기록이 최대 5.8MB다. 전체를 파싱하면 갱신마다 수백 ms 가 날아간다.
**역순으로 필요한 레코드까지만** 읽는다.

## 범위 밖 (명시)

- 세션 조작 (종료·재개·프롬프트 전송)
- 대화 내용 전문 표시 — 제목과 마지막 프롬프트 한 줄까지만
- 중앙 서버 · 계정 · 인증
- 다른 사람의 세션 조회
- 원격 기계 통합 — 1차 범위 밖. [04-배포](04-배포.md) 참고

## 미결 사항 — 착수 전 확인할 것

### 1. 브랜치 전략

작업협약 6번 표준 계층은 `main ← stg ← dev ← feature/*` 이다.
다만 같은 문서에 **"기여자가 1명이고 feature 가 동시에 진행되지 않으면
`dev` 는 병합만 늘리고 얻는 게 없다"** 고 적혀 있다.

이 저장소는 개인 도구이고 기여자 1명이다.
→ **`main` + `feature/*` 만 두는 것을 제안한다.** 사용자 확인 필요.
(작업협약은 "혼자 판단해서 생략하지 말고 사용자에게 물으라"고 명시)

확정되면 이 문서와 `CLAUDE.md` 에 근거를 남길 것.

### 2. 이슈 트래커

작업협약 1번 "모든 작업은 이슈 생성으로 시작".
GitHub Issues 를 쓸지, 원격 저장소를 만들지 미정.
→ 원격 저장소 생성은 외부 공개 행위이므로 사용자 승인 후 진행.

### 3. 컨텍스트 상한

컨텍스트 사용률(%)을 계산하려면 모델별 상한을 알아야 한다.
세션 기록에서 모델명을 읽을 수 있으나, 모델→상한 표를 하드코딩할지
토큰 절대값만 표시할지 미정.
→ **1차는 절대값(예: `458K`)만 표시**하고, 상한 표는 나중에 검토.
