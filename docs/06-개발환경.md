# 06. 개발 환경

새 기계나 새 세션에서 착수할 때 필요한 것들. 실측으로 걸렸던 함정을 포함한다.

## 준비

### JDK 21

```bash
brew install openjdk@21
```

⚠️ **Homebrew 의 `openjdk@21` 은 keg-only 라 PATH 에 안 잡힌다.**
`java -version` 이 "Unable to locate a Java Runtime" 을 뱉어도
**설치가 안 된 게 아니라 연결이 안 된 것**일 수 있다. 확인:

```bash
ls /opt/homebrew/opt/ | grep -i jdk        # openjdk@21 이 보이면 설치돼 있다
/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home/bin/java -version
```

Gradle 에 알려주는 방법 — 셋 중 하나:

```bash
# ① 그 세션에서만
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home

# ② 영구 (~/.zshrc)
echo 'export JAVA_HOME=$(/usr/libexec/java_home -v21 2>/dev/null || echo /opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home)' >> ~/.zshrc

# ③ 시스템에 연결 (sudo 필요)
sudo ln -sfn /opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk \
  /Library/Java/JavaVirtualMachines/openjdk-21.jdk
```

`build.gradle.kts` 가 toolchain 으로 21 을 요구하므로 다른 버전이 잡혀 있어도 된다.

### pre-commit 훅

**클론할 때마다 한 번 설정해야 한다** (git 은 훅을 클론하지 않는다):

```bash
git config core.hooksPath .githooks
```

되돌리기 검증(뮤테이션) 잔재가 커밋에 섞이는 것을 막는다.
`MUTATION`·`MUTATED`·`MUTANT` 세 형태를 모두 잡는다.

설정됐는지 확인:
```bash
git config core.hooksPath    # → .githooks
```

## 자주 쓰는 명령

```bash
./gradlew build              # 컴파일 + 테스트
./gradlew test               # 테스트만
./gradlew bootJar            # jar 생성 → build/libs/claude-board.jar

# 수집 결과를 눈으로 보기 (웹 서버 없이)
java -jar build/libs/claude-board.jar --json | jq -r '.projects[] |
  "\(.current.state)\t\(.name)"'

# 벤치마크 (기본은 스킵됨 — 이 기계의 실제 세션 기록을 읽는다)
./gradlew test --tests '*ReaderBenchmark*' -Dbenchmark=true -i
```

## IDE — 무엇을 써도 된다

**이 저장소는 특정 IDE 를 전제하지 않는다.** `collect/` 구현 전체가
터미널 + Claude Code 로 진행됐고 IDE 가 필요한 순간이 없었다.

### IntelliJ 를 쓴다면

`File → Open` 으로 **저장소 루트**를 열면 된다. Gradle 프로젝트로 자동 인식된다.
`frontend/` 가 생기면 npm 스크립트도 같은 창에서 잡힌다.

Community(무료) 로 충분하다. Ultimate 에서만 되는 것은
Spring Bean 그래프·`application.yml` 메타데이터 힌트 정도이고,
디버거·리팩터링 엔진은 Community 도 같다.

**IDE 가 실제로 필요해지는 시점**은 "디버거가 있어야 풀리는 문제"를 만났을 때다
(SSE 연결이 안 붙는데 원인 불명, Bean 주입이 꼬임 등).
그 전까지는 테스트가 pass/fail 을 명확히 주므로 없어도 된다.

### Claude Code 생태계는 IDE 와 무관하다

세션 기록(`~/.claude/projects/*.jsonl`)은 **어디서 실행했든 동일하게 쌓인다** —
터미널·Cursor·VS Code·IntelliJ 무관. 그래서:

- IDE 를 바꿔도 **이 대시보드는 그대로 작동한다**
- `~/.claude/` 의 전역 설정·규칙·스킬도 실행 위치와 무관하게 로드된다
- IntelliJ 안에서도 그냥 터미널을 열어 `claude` 를 치면 된다
  (Anthropic 공식 JetBrains 플러그인도 있지만 필수는 아니다)

## 저장소 구조 — 왜 하나인가

**FE 와 BE 를 나누지 않는다.** 이유는 IDE 가 아니라 **배포 단위**다.

| 레포 분리가 맞는 경우 | 이 프로젝트 |
|---|---|
| BE·FE 가 따로 배포됨 | ❌ 단일 jar 에 FE 가 들어간다 |
| 팀이 달라 권한 분리 필요 | ❌ 기여자 1명 |
| FE 를 다른 BE 에서도 재사용 | ❌ 이 백엔드 전용 |
| 릴리스 버전이 따로 감 | ❌ 항상 같이 나간다 |

Vue 빌드 결과가 `src/main/resources/static/` 으로 들어가 **하나의 산출물**이 된다
([04-배포](04-배포.md)). 나누면 빌드 결과를 옮기거나 서브모듈을 붙여야 해서
얻는 것 없이 일만 는다.

같은 이유로 **모노레포 도구(pnpm workspace, Gradle 멀티프로젝트)도 쓰지 않는다.**
그 도구들이 푸는 문제는 "여러 산출물이 서로 다른 주기로 배포되며 버전을 맞춰야 함"인데
여기엔 그 문제가 없다.

```
claude-board/
├── src/                  # 백엔드 (Java)
├── frontend/             # 프론트 (Vue) — 다음 이슈에서 생성
├── docs/
└── .githooks/
```

FE 작업 시 IDE 가 무겁게 느껴지면 **레포를 나누는 게 아니라 창을 두 개 연다**
(IntelliJ 로 루트, 다른 에디터로 `frontend/`).

## CI

`.github/workflows/ci.yml`. PR 이 `main` 으로 갈 때 돈다.

| 잡 | 언제 | 무엇 |
|---|---|---|
| `changes` | 항상 | 어느 영역이 바뀌었는지 판단 |
| `backend` | `src/**` 등 변경 시 | 빌드·테스트 + jar 에 세션 데이터 없는지 + 바인딩 검사 |
| `frontend` | `frontend/**` 변경 시 | 타입체크·린트·단위테스트·빌드 |
| `e2e` | `frontend/**` 변경 시 | Playwright |
| `ci` | 항상 | **브랜치 보호가 요구하는 단일 게이트** |

`ci` 게이트는 스킵을 통과로 보되 **실패·취소는 통과시키지 않는다.**
개별 잡은 변경 영역에 따라 스킵되므로 브랜치 보호에는 `ci` 하나만 지정한다.

### 브랜치 보호 (설정됨)

```
required_status_checks : ["ci"], strict
enforce_admins         : true      ← 관리자도 우회 못 한다
allow_force_pushes     : false
allow_deletions        : false
```

확인:
```bash
gh api repos/chahyunwoo/claude-board/branches/main/protection --jq '{
  checks: .required_status_checks.contexts,
  enforce_admins: .enforce_admins.enabled }'
```

⚠️ **게이트 작동을 확인할 때 보호 대상 브랜치를 실제로 움직이지 말 것.**
실측(2026-09-03): `git push origin feature/1:main` 으로 검사하려다
**PR 이 실제로 머지됐다.** `--dry-run` 은 클라이언트 측이라 서버 훅 판정을 안 타므로
"dry-run 통과 = 보호 없음" 이 아니다. 검사가 필요하면 CI 를 안 돌린 커밋을
임시 브랜치에서 밀어 거부되는지 본다.

또한 required status check 는 "그 커밋에 성공한 체크가 있는가"를 본다 —
**이미 CI 가 초록인 커밋을 밀면 통과하는 것이 정상 동작**이지 구멍이 아니다.
