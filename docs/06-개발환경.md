# 06. 개발 환경

새 기계나 새 세션에서 착수할 때 필요한 것들. 실측으로 걸렸던 함정을 포함한다.

## 준비

### JDK 21

```bash
brew install openjdk@21
```

⚠️ **Homebrew 의 `openjdk@21` 은 keg-only 라 PATH 에 안 잡힌다.**
`java -version` 이 "Unable to locate a Java Runtime" 을 뱉어도
**설치가 안 된 게 아니라 연결이 안 된 것**일 수 있다. 확인:

```bash
ls /opt/homebrew/opt/ | grep -i jdk        # openjdk@21 이 보이면 설치돼 있다
/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home/bin/java -version
```

Gradle 에 알려주는 방법 — 셋 중 하나:

```bash
# ① 그 세션에서만
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home

# ② 영구 (~/.zshrc)
echo 'export JAVA_HOME=$(/usr/libexec/java_home -v21 2>/dev/null || echo /opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home)' >> ~/.zshrc

# ③ 시스템에 연결 (sudo 필요)
sudo ln -sfn /opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk \
  /Library/Java/JavaVirtualMachines/openjdk-21.jdk
```

`build.gradle.kts` 가 toolchain 으로 21 을 요구하므로 다른 버전이 잡혀 있어도 된다.

### pre-commit 훅

**클론할 때마다 한 번 설정해야 한다** (git 은 훅을 클론하지 않는다):

```bash
git config core.hooksPath .githooks
```

되돌리기 검증(뮤테이션) 잔재가 커밋에 섞이는 것을 막는다.
`MUTATION`·`MUTATED`·`MUTANT` 세 형태를 모두 잡는다(어간 `MUTAT` + `MUTANT`).

**검사 대상은 코드다 — `docs/` 는 제외한다.** 뮤테이션 잔재는 소스에 남는 문제이고,
문서는 이 패턴을 **설명하려고 인용**해야 하기 때문이다(지금 이 줄이 그렇다).
제외하지 않으면 훅을 설명하는 문서가 훅에 막혀 영영 커밋되지 않는다.

⚠️ **훅이 있다 ≠ 훅이 작동한다.** 고친 뒤에는 반드시 세 형태를 **한글·영문 파일명 양쪽에**
넣어보고 전부 거부되는지 확인한다 — 아래 "훅이 실제로 작동하는지 확인" 참고.

설정됐는지 확인:
```bash
git config core.hooksPath    # → .githooks
```

#### ⚠️ 훅이 실제로 작동하는지 확인 — 설정 확인만으로는 부족하다

**실측 (#13)**: 훅이 설정돼 있고 실행권한도 있는데 **한글 파일명을 전혀 검사하지
못하고 있었다.** 이 저장소의 문서는 전부 한글 파일명이라, 훅이 있는 채로
문서에 잔재를 넣어도 **여섯 번 다 통과했다.**

원인은 `git diff --cached --name-only` 가 ASCII 밖의 경로를 **따옴표로 감싸
이스케이프**해서 내놓기 때문이다:

```bash
$ git diff --cached --name-only
"docs/03-\355\224\204\353\241\240\355\212\270.md"    # ← 이런 문자열
```

이걸 `git grep` 에 경로로 넘기면 그런 파일이 없어서 **아무것도 검사하지 못하고
조용히 통과한다.** 예외도 에러도 없다 — 게이트가 죽었는데 초록으로 보인다.
`-z`(NUL 구분)로 받으면 이스케이프가 붙지 않는다.

고친 뒤에는 **세 형태를 한글·영문 파일명 양쪽에 넣어 전부 거부되는지 센다**:

```bash
for word in MUTATION MUTATED MUTANT; do
  for f in frontend/src/lib/한글테스트.ts frontend/src/lib/asciitest.ts; do
    printf '// %s\n' "$word" > "$f"; git add -A
    sh .githooks/pre-commit >/dev/null 2>&1 \
      && echo "✗ $word in $f 통과됨" || echo "✓ $word in $f 거부됨"
    rm -f "$f"
  done
done
git add -A
# → 6건 전부 "거부됨" 이어야 한다. 그 뒤 깨끗한 상태에서 통과하는 것도 본다.
```

작업협약 7번 **"게이트가 있다 ≠ 게이트가 작동한다"** 의 실제 사례다.

**이 검사는 CI 의 `hooks` 잡으로 강제된다** — `.githooks/**` 가 바뀌면 자동으로 돈다.
손으로 기억해서 돌리는 것에 맡기지 않는다(작업협약 5번: 매번 일어나야 하는 일은
텍스트 지시가 아니라 게이트로 만든다).

그 잡이 **실제로 고장을 잡는지도 확인했다** — 훅을 원래 버그(`-z` 제거) 상태로
되돌리자 한글 파일명 3건만 실패하고 영문은 통과했다. 실제 버그의 형태 그대로다.

⚠️ 훅의 제외 목록에 `.github/workflows/` 가 있는 것은 이 잡 때문이다 —
CI 스크립트가 세 형태를 문자열로 담고 있어, 제외하지 않으면 **훅을 검사하는 CI 가
훅에 막혀 커밋되지 않는다.** 같은 이유로 `docs/` 도 제외한다.

## 자주 쓰는 명령

```bash
./gradlew build              # 컴파일 + 테스트
./gradlew test               # 테스트만
./gradlew bootJar            # jar 생성 → build/libs/claude-board.jar

# 수집 결과를 눈으로 보기 (웹 서버 없이)
java -jar build/libs/claude-board.jar --json | jq -r '.projects[] |
  "\(.current.state)\t\(.name)"'

# 벤치마크 (기본은 스킵됨 — 이 기계의 실제 세션 기록을 읽는다)
./gradlew test --tests '*ReaderBenchmark*' -Dbenchmark=true -i
```

### 프론트 (`frontend/` 에서)

```bash
npm ci                       # 설치 (package-lock.json 기준 — CI 와 같은 버전)

npm run dev                  # dev 서버 :5173, /api 는 127.0.0.1:7777 로 프록시
npm run build                # → ../src/main/resources/static/

npm run type-check           # vue-tsc
npm run lint                 # biome check .        (린트 + 포맷 검사)
npm run format               # biome check --write .  (자동 수정)
npm run test:unit            # vitest
npm run test:e2e             # playwright (첫 실행 전 npx playwright install chromium)
```

**`npm run dev` 는 백엔드가 떠 있어야 데이터가 보인다.** 프록시라 CORS 를 열지 않는다 —
여는 순간 "데이터는 이 기계를 떠나지 않는다" 의 경계가 흐려진다.

전체를 한 번에 보려면 프론트를 빌드해 jar 에 넣고 `:7777` 하나만 띄운다:
```bash
(cd frontend && npm run build) && ./gradlew bootJar
java -jar build/libs/claude-board.jar        # http://127.0.0.1:7777
```

## IDE — 무엇을 써도 된다

**이 저장소는 특정 IDE 를 전제하지 않는다.** `collect/`·`web/`·`frontend/` 구현이
전부 터미널 + Claude Code 로 진행됐고 IDE 가 필요한 순간이 없었다.

### IntelliJ 를 쓴다면

`File → Open` 으로 **저장소 루트**를 열면 된다. Gradle 프로젝트로 자동 인식되고,
`frontend/package.json` 의 npm 스크립트도 같은 창에서 잡힌다.

Community(무료) 로 충분하다. Ultimate 에서만 되는 것은
Spring Bean 그래프·`application.yml` 메타데이터 힌트 정도이고,
디버거·리팩터링 엔진은 Community 도 같다.

**IDE 가 실제로 필요해지는 시점**은 "디버거가 있어야 풀리는 문제"를 만났을 때다
(SSE 연결이 안 붙는데 원인 불명, Bean 주입이 꼬임 등).
그 전까지는 테스트가 pass/fail 을 명확히 주므로 없어도 된다.

### Claude Code 생태계는 IDE 와 무관하다

세션 기록(`~/.claude/projects/*.jsonl`)은 **어디서 실행했든 동일하게 쌓인다** —
터미널·Cursor·VS Code·IntelliJ 무관. 그래서:

- IDE 를 바꿔도 **이 대시보드는 그대로 작동한다**
- `~/.claude/` 의 전역 설정·규칙·스킬도 실행 위치와 무관하게 로드된다
- IntelliJ 안에서도 그냥 터미널을 열어 `claude` 를 치면 된다
  (Anthropic 공식 JetBrains 플러그인도 있지만 필수는 아니다)

## 저장소 구조 — 왜 하나인가

**FE 와 BE 를 나누지 않는다.** 이유는 IDE 가 아니라 **배포 단위**다.

| 레포 분리가 맞는 경우 | 이 프로젝트 |
|---|---|
| BE·FE 가 따로 배포됨 | ❌ 단일 jar 에 FE 가 들어간다 |
| 팀이 달라 권한 분리 필요 | ❌ 기여자 1명 |
| FE 를 다른 BE 에서도 재사용 | ❌ 이 백엔드 전용 |
| 릴리스 버전이 따로 감 | ❌ 항상 같이 나간다 |

Vue 빌드 결과가 `src/main/resources/static/` 으로 들어가 **하나의 산출물**이 된다
([04-배포](04-배포.md)). 나누면 빌드 결과를 옮기거나 서브모듈을 붙여야 해서
얻는 것 없이 일만 는다.

같은 이유로 **모노레포 도구(pnpm workspace, Gradle 멀티프로젝트)도 쓰지 않는다.**
그 도구들이 푸는 문제는 "여러 산출물이 서로 다른 주기로 배포되며 버전을 맞춰야 함"인데
여기엔 그 문제가 없다.

```
claude-board/
├── src/                  # 백엔드 (Java)
│   └── main/resources/static/   # ← Vue 빌드 결과가 여기 떨어진다 (산출물, 커밋 안 함)
├── frontend/             # 프론트 (Vue)
│   ├── src/lib/          # 타입·서식·그룹핑·SSE 구독
│   ├── src/components/
│   └── e2e/              # Playwright
├── docs/
└── .githooks/
```

⚠️ **`src/main/resources/static/` 은 산출물이라 커밋하지 않는다** (`.gitignore`).
`frontend/` 에서 `npm run build` 하면 생기고 `bootJar` 가 그것을 jar 에 넣는다.
커밋하면 소스와 산출물이 어긋난 채 배포되는 경로가 생긴다.
그래서 **백엔드만 클론한 직후에는 이 디렉터리가 없다** — 정상이다
(Spring 은 정적 리소스가 없으면 없는 대로 뜬다). 화면을 보려면 프론트를 먼저 빌드한다.

FE 작업 시 IDE 가 무겁게 느껴지면 **레포를 나누는 게 아니라 창을 두 개 연다**
(IntelliJ 로 루트, 다른 에디터로 `frontend/`).

## CI

`.github/workflows/ci.yml`. PR 이 `main` 으로 갈 때 돈다.

| 잡 | 언제 | 무엇 |
|---|---|---|
| `changes` | 항상 | 어느 영역이 바뀌었는지 판단 |
| `hooks` | `.githooks/**` 변경 시 | **훅이 실제로 잡는지** 전수 검사 (아래) |
| `backend` | `src/**` 등 변경 시 | 빌드·테스트 + jar 에 세션 데이터 없는지 + 바인딩 검사 |
| `frontend` | `frontend/**` 변경 시 | 타입체크·린트·단위테스트·빌드 |
| `e2e` | `frontend/**` 변경 시 | Playwright |
| `ci` | 항상 | **브랜치 보호가 요구하는 단일 게이트** |

`ci` 게이트는 스킵을 통과로 보되 **실패·취소는 통과시키지 않는다.**
개별 잡은 변경 영역에 따라 스킵되므로 브랜치 보호에는 `ci` 하나만 지정한다.

### 액션 버전 — CI 로그의 경고를 읽는다

**실측 (#25)**: `setup-java v4 is deprecated` 경고가 CI 로그에 있었는데
**CI 는 초록이라 아무도 안 봤다.** 세어보니 6개 액션 전부 메이저가 밀려 있었다 —
경고는 하나만 떴지만 나머지도 같은 길을 간다.

```bash
# 현재 버전과 최신을 대조한다
for a in $(grep -oE 'uses: [^@]+' .github/workflows/ci.yml | sed 's/uses: //' | sort -u); do
  repo=$(echo "$a" | cut -d/ -f1,2)
  cur=$(grep -oE "$a@v[0-9]+" .github/workflows/ci.yml | head -1 | grep -oE 'v[0-9]+$')
  latest=$(curl -s "https://api.github.com/repos/$repo/releases/latest" | jq -r '.tag_name')
  printf '%-32s %s → %s\n' "$a" "$cur" "$latest"
done
```

⚠️ **버전만 올리고 통과를 기대하지 않는다.** 릴리스 노트를 읽고 우리가 쓰는 옵션에
영향이 있는지 본다. 우리는 표준 옵션(`java-version`/`distribution`,
`node-version`/`cache`, `name`/`path`/`retention-days`)만 써서 영향이 없었다.

⚠️ **초록이어도 로그를 읽는다.** 이번 경고가 정확히 그렇게 묻혀 있었다.

⚠️ **치환 개수를 세어서 고정한다.** `checkout` 이 4곳인 줄 알고 바꿨는데
`assert s.count(old) == 4` 가 **실제 5곳**임을 잡았다 — 없었으면 1곳이 구버전으로 남았다.

### 브랜치 보호 (설정됨)

```
required_status_checks : ["ci"], strict
enforce_admins         : true      ← 관리자도 우회 못 한다
allow_force_pushes     : false
allow_deletions        : false
```

확인:
```bash
gh api repos/chahyunwoo/claude-board/branches/main/protection --jq '{
  checks: .required_status_checks.contexts,
  enforce_admins: .enforce_admins.enabled }'
```

⚠️ **게이트 작동을 확인할 때 보호 대상 브랜치를 실제로 움직이지 말 것.**
실측(2026-09-03): `git push origin feature/1:main` 으로 검사하려다
**PR 이 실제로 머지됐다.** `--dry-run` 은 클라이언트 측이라 서버 훅 판정을 안 타므로
"dry-run 통과 = 보호 없음" 이 아니다. 검사가 필요하면 CI 를 안 돌린 커밋을
임시 브랜치에서 밀어 거부되는지 본다.

또한 required status check 는 "그 커밋에 성공한 체크가 있는가"를 본다 —
**이미 CI 가 초록인 커밋을 밀면 통과하는 것이 정상 동작**이지 구멍이 아니다.
