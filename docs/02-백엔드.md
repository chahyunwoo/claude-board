# 02. 백엔드

## 스택

| | 선택 | 이유 |
|---|---|---|
| 언어 | **Java 21** | record · pattern matching · virtual thread 사용 가능 |
| 프레임워크 | **Spring Boot 3** | 실무 스택. 이 도구가 요구하는 것들이 Spring 실무 패턴과 겹친다 |
| 빌드 | **Gradle (Kotlin DSL)** | |
| 테스트 | **JUnit 5 + AssertJ** | |

### 왜 Spring 인가 — 이 프로젝트가 요구하는 것들

억지 근거가 아니라 실제로 겹친다.

| 이 도구에 필요한 것 | Spring 요소 |
|---|---|
| 5초마다 세션 수집 | `@Scheduled` |
| 실시간 갱신 | `SseEmitter` |
| `claude agents --json` 실행 | `ProcessBuilder` |
| 대용량 파일 역순 읽기 (최대 21MB) | NIO `RandomAccessFile` |
| 상태 판별 | 순수 도메인 로직 + JUnit |
| API 스키마 | `record` DTO |

### 포기하는 것 (알고 간다)

```
설치:  npm i -g 한 줄  →  ./gradlew bootRun 또는 jar
기동:  ~100ms          →  JVM 부팅
전제:  없음             →  JDK 21 필요
```

개인 도구로 쓰는 동안엔 실질 문제가 아니다.
남에게 배포할 단계가 오면 GraalVM native-image 를 검토한다 ([04-배포](04-배포.md)).

## 핵심 — `TranscriptReader`

최대 21MB 파일을 전부 읽으면 안 된다.

```
파일 끝에서 64KB 씩 뒤로 읽으며 줄 단위 역순 순회
필요한 필드(aiTitle · lastPrompt · gitBranch · model · usage
             · 마지막 대화 레코드)를 모두 채우면 즉시 중단
64KB 로 못 채우면 다음 청크로 확장. 상한 512KB, 넘으면 부분 결과 반환
```

부분 결과라도 반환한다. 제목이 없어도 상태 판별은 되어야 한다.

`RandomAccessFile.seek()` 으로 읽고, JSON 파싱은 Jackson `ObjectMapper.readTree()` 로 줄 단위.

### 구현하며 걸린 함정 세 가지

**① 청크 경계에 걸친 줄을 이어붙여야 한다.**
64KB 로 자르면 줄 중간이 잘린다. 앞 조각을 보류했다가 다음(더 앞쪽) 청크의
마지막 줄과 이어붙이지 않으면 깨진 JSON 으로 보여 **조용히 건너뛰게 된다.**

**② 상한 검사는 파싱 *뒤*에 한다.**
파싱 앞에서 끊으면 상한이 청크 크기(64KB)보다 작을 때 첫 줄조차 못 읽어
`lastRecordKind` 가 비고 **상태 판별이 통째로 죽는다.**
상한은 "더 읽을지"의 기준이지 "이미 읽은 것을 버릴지"의 기준이 아니다.

**③ `permissionMode` 를 완료 조건에 넣지 말 것.**
일부 레코드에만 있다(실측: user 158개 중 14개). 완료 조건에 넣으면
**매번 상한까지 읽게 된다.** 없으면 없는 대로 부분 결과로 낸다.

## 설정

`application.yml`
```yaml
server:
  address: 127.0.0.1        # 반드시. 0.0.0.0 금지
  port: 7777

claude-board:
  interval: 5s              # 수집 주기
  stalled-after: 10m        # 멈춤 의심 임계
  idle-after: 2h            # 유휴 임계
  context-limit: 1000000    # 컨텍스트 상한 기본값. 관측값이 넘으면 자동 상향
  transcript-max-bytes: 512KB # 역순 읽기 상한. 근거는 아래
```

### `transcript-max-bytes` — 512KB 인 이유

상한별 소요와 정보 손실을 실측해서 골랐다 (파일 109개 / 총 327MB / 최대 21MB):

```
  상한    시간    lastPrompt 누락
   64K    58ms      49 / 109
  128K    63ms      27 / 109
  256K    71ms      16 / 109
  512K    87ms       6 / 109   ← 선택
 1024K   121ms       3 / 109
```

1MB 대비 시간은 24% 줄고 누락은 3개만 는다.

재현:
```bash
./gradlew test --tests '*ReaderBenchmark*' -Dbenchmark=true -i
```

⚠️ 벤치마크는 **이 기계의 실제 세션 기록을 읽으므로** `-Dbenchmark=true` 없이는
스킵된다. CI 에는 그 데이터가 없어 결과가 무의미하다.

## 컨텍스트 상한 — 주의

세션 기록의 모델명은 `claude-opus-5` 로만 남고 **`[1m]` 변형이 구분되지 않는다.**
실측에서 671,229 토큰이 관측됐으므로 그 세션은 1M 모델인데 기록으로는 알 수 없다.

→ 설정의 `context-limit` 을 기본값으로 쓰되,
**관측 토큰이 그 값을 넘으면 상한을 자동으로 올린다.**
표시는 `절대값 / 상한 · %` 세 가지를 모두 낸다 (분모가 틀려도 절대값으로 판단 가능).

## 전체 갱신 200ms — 병목은 이 저장소 밖에 있다

`--json` 전체 수집이 **285ms** 로 목표를 넘는다. 구간을 나눠 실측했다:

```bash
# claude agents --json 단독 5회
201ms 202ms 207ms 204ms 199ms
```

**~200ms 가 `claude agents --json` 서브프로세스 자체**(Node CLI 부팅)다.
우리 파일 읽기는 나머지 ~80ms 이고, 역순 리더는 전체 파싱 대비 15.9배 빠르다.

→ 즉 리더를 더 최적화해도 소용없다. **`@Scheduled` 로 백그라운드에서 수집해 캐시하고,
화면 갱신은 캐시를 읽으면** 체감 지연이 사라진다. 7번에서 이 구조로 간다.
